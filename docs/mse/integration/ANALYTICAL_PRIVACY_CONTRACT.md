## Proposed purpose-limited views

Version the analytical interface separately, provisionally `mse.analytics-view/0.1`. Default deny. A purpose registry chooses an explicit view, policy version, allowed recipient, eligible scope, expiry, allowed columns, date/value precision and query budgets. The service enforces these parameters independently of caller-supplied fields. Ingestion credentials cannot read views. Analytics credentials cannot access raw data, linkage mappings, direct ledger APIs or archival rows.

| View | Allowlist and analytical limits |
| --- | --- |
| Protected MSE execution | Run byte-bound 0.2 snapshots within an authorized local execution boundary. Preserve exact event intervals and ordering, required receipt semantics, SDNN class, unit and cutoff. Resolve authoritative revision and deletion in that boundary. Export only a separately reviewed result. The model input remains sensitive pseudonymous evidence. |
| Restricted longitudinal analysis | Allow a purpose-scoped random subject token only when longitudinal grouping is needed. Use explicitly selected relative time or approved granularity, channel/unit, allowed precision or aggregate, and coarse uncertainty/coverage. Elapsed time can retain routine and rare-event signatures. Exact calendar, time-zone/context, source and receipt clues require separately authorized access. No UUID, source/store/app/device ID, hashes, locator, raw original number token or stable operational sequence. |
| Aggregate evaluation | Prefer approved aggregate-only outputs when the task does not need individual sequences. Limit repeated overlapping queries and exports. Apply reviewed suppression and cohort/granularity rules for rare or sparse events. Single-subject output should stay within a protected environment when release risk cannot be bounded. |

Use random tokens independent across purposes and domains, with mapping in a restricted linkage vault under separate access and key custody. Do not derive public tokens from UUIDs, dates or batch digests. Renewal, revocation and erasure must invalidate affected current views and derived availability without changing authoritative source facts or retroactively changing historical receipt evidence. Keep exact per-revision lineage inside restricted custody and expose only a purpose-scoped view identifier or non-linking aggregate. Treat derived outputs, vector embeddings, debug logs, temporary paths, exports, backups and WAL/sidecars as governed surfaces.

Proposed view envelope: `schema_version`, opaque purpose-scoped `view_id`, approved `purpose`, `policy_version`, `projection_version`, `time_basis`, `rows`, and coarse `projection_loss`. Version the row allowlist per purpose. An exact protected manifest binds this to source snapshot, cutoff, input/output digests, transform/version, authorized scope/recipient, time policy, loss counts, expiration and revocation generation. Restrict the manifest and mapping rather than duplicating source identifiers in an outward response. Use bounded retention for projections. The authoritative archive and frozen 0.2 remain untouched.

A time transform must disclose its method, granularity and effect on ordering, durations, phase, clock alignment, cutoff admissibility, missingness and loss. Compute eligible authoritative revisions before projection. If a purpose needs exact periodic or cross-source chronology, use the protected MSE boundary or reject the reduced view for that purpose. A shifted or binned timestamp cannot be consumed as if it were an actual authoritative time. Never claim reduced identity prevents all linkage. Evaluate the sharing model and residual disclosure risk against a correlator with auxiliary data, consistent with the primary guidance. [NIST SP 800-188](https://csrc.nist.gov/pubs/sp/800/188/final)
