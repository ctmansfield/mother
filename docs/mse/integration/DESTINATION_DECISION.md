### Choose a trust boundary

1. **Separate volumes on one host.** For a synthetic trial, separate service identities and encrypted evidence and analytical volumes are an economical rehearsal. This can limit ordinary service access. An administrator on the same unlocked host may still cross both boundaries. An identity vault on that same administrative boundary does not satisfy an attacker model that includes host-root compromise.
2. **Separate vault and analytics administration.** For a future personal-data design, prefer a vault under distinct administrative and key custody. Keep the authoritative evidence archive restricted. Allow a narrow projection publisher to request approved scoped tokens, then write only the versioned analytical view. The analytical worker cannot resolve tokens or query original files. A compromised writer can still expose entrusted inputs, and an unauthorized copy of the projection can still be linked using time patterns or external data. Use purpose and release-risk review to decide what leaves the restricted domain. [NIST de-identification guidance](https://csrc.nist.gov/pubs/sp/800/188/final)

### Owner decisions before runtime qualification

- **Boundary and roles.** Chad and SENTINEL agree which adversaries the deployment must contain. Name separate evidence writer, vault custodian, projection publisher, analytical reader and backup custodian. Select the actual host or administrative boundary for each and test denial of cross-domain access. If root compromise is in scope, choose independently administered vault and backup boundaries instead of same-host privileges alone.
- **Recovery keys.** Assign separate encryption/key domains for restricted evidence, vault mappings and analytical data. Record active and recovery key versions and controlled recovery references in private custody. Keep recovery material separate from encrypted backups. Require an approved two-person restore gate for vault recovery, test key loss and revocation separately, and retain only historical key versions required by retained generations. Decide rotation, recovery quorum, break-glass scope and expiration explicitly. [NIST key management guidance](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final)
- **Restore and invalidation.** Recover a coherent generation into isolated access under its matching schema and key versions. Verify ciphertext/authentication and bindings without exposing originals in ordinary logs. Reapply current policy and erasure state before publication, reconcile any withheld or deleted links, and invalidate stale derived snapshots and memory references. Never restore the analytical view by exposing the vault to the analytical worker.
- **Release policy.** Decide which scope and chronology are necessary for each analytical purpose, which fields are transformed or suppressed, and what linkage-risk review is required. Preserve exact provenance separately. Do not characterize hashing, access control or encrypted disks as de-identification by themselves.
