## Enrollment and time fence

Freeze one immutable enrollment, with a fresh pilot identifier and a deliberately new source-instance namespace, for the intended signed app, approved private HTTPS endpoint and dedicated selected archive. Both sides compare the exact approved archive ID and four-field scope from their trusted configurations; no caller-provided archive or phase selection. Do not reuse legacy or synthetic namespaces, keys, tokens, anchors, stores or routes. The selected type set is exactly the 14 metrics in the pinned contract. Optional unavailable types may yield no records.

Staging permits source/build qualification, installation and permissions in the directed order. It leaves live acquisition queue publication and phone/server sends disabled. Only GADGET's readiness GO records the actual start and end, paired phone/server configuration digests and authorized operator. The enrolment covers a half-open UTC interval `[start,end)`, where `end = start + 172800 seconds`. Use exact canonical UTC instants and publish equivalent Guam times in the sanitized release receipt. The release record uses trusted server UTC; client expiry must independently stop even if requests fail. A backward, untrusted or inconsistent clock must never extend the enrollment. Reject malformed, unequal or unavailable window state. A restart uses the same enrollment and window. Never extend or re-enroll automatically.

## Eligible records and source clocks

| Case | Rule |
| --- | --- |
| Fresh progress | Start a separate per-selected-type query and checkpoint for this enrollment. Never read a legacy collector file into the selected outbox, import a historical anchor or fall back to unfiltered backfill. Fixed lower bound is the approved start. Keep the original collector and legacy anchors untouched. Tighten the query with the approved endpoint bounds when the API supports it, and enforce interval filtering in both app and server regardless of predicate behavior. Persist only admitted selected facts in the pilot outbox. |
| Point samples | Require `start <= event_start == event_end < end`, interval complete at observation, and in-window collector receipt. The server checks the original claim against its own current UTC, plus explicit configured clock-tolerance policy if reviewed. Never use tolerance to widen the approved window. A point exactly at cutoff is out of scope. |
| Interval quantities, sleep and workout | Eligible only if source start is at or after pilot start and before cutoff, and source end is at or before cutoff, with a completed interval visible before cutoff. A sleep episode, sleep stage, cumulative quantity or workout with a source interval crossing either boundary is excluded as a whole. Never clip or prorate intervals, shift times, split cumulative values, infer missing sleep stages, count out-of-window totals or fabricate workout duration. Treat independently recorded source intervals independently; overlapping valid stages or contributors remain distinct. A boundary interval that completes only at cutoff cannot begin a new upload then. |
| Delayed HealthKit visibility | Separate event time, collector receipt, first server receipt and durable commit. Initial source availability is null. A late-discovered sample can enter only if its entire event satisfies the boundary and collection and ingestion still occur within the window. Unavailable clock or containment evidence excludes the row with a coarse reason. No delayed source retry beyond cutoff. |
| Deletion and replacement | Only emit an in-window deletion for an already enrolled eligible key in the pilot's persisted local admitted-key set, or for a paired eligible add in the same immutable batch. The server verifies earlier accepted or same-batch membership in the selected scope before treating the deletion as admitted. Do not emit unaffiliated historical unknown-UUID deletions during this prospective pilot. An observed eligible add followed by deletion in one batch retains both facts and suppresses the current row. A replacement with a different UUID is a new fact, with explicit deletion of the old eligible key if observed. Missing sample or lost permission is no deletion. Keep tombstoned pilot history and suppress the current key at and after its authoritative deletion commit. |
| Availability | Use individual supported/unsupported, visible, empty-coverage-unknown, query error and never-queried states. Empty or partial HealthKit responses give neither a zero nor proof of permission, absence or uninterrupted collection. A true source zero is still a source fact, with processing exclusion when applicable. Expose sanitized last collected/queued/acked times, counts and status. Body values, source names, arbitrary metadata and workout routes remain private or excluded per the selected contract. |

Pilot query ordering, eligibility and type accounting are distinct from completeness. Report boundary exclusions, observed misses, delayed availability, blocked permissions and stopped work as coarse counts. A 48-hour gap or sample timing says nothing about clinical condition. No uninterrupted real-time guarantee.

## Cutoff, pending bytes and archival retention

From the first in-window collection commit onward keep exact outbox bytes, batch identity, digest, and binding stable through retries and offline/restart. Persist acquisition progress only after enqueue and evidence for deliberately excluded rows agree. Pause responsive producers/backpressure when the private queue or server quota is reached; avoid discard as a way to advance anchors. Only a strict matching normalized receipt dismisses an in-flight item. Rejection or conflict stops that batch and preserves evidence. Custody-only is not acknowledgment.

Client stops collection for this enrollment and starts no further PUT/retry at cutoff. Cancel active sends when possible and keep their unacknowledged bytes immutable. Do not send them after restart, forward via a different scope, or count them as archived. If the result is uncertain, record the status without relaunching delivery. A terminal response after cutoff cannot by itself establish an authorized new commit. Only an already committed, verified pre-cutoff receipt obtained through separately authorized operator readback can reconcile the record historically. The default client no longer accesses or automatically acknowledges its pending queue after cutoff.

The server disallows new body admission, original/revision mutation and new sequence allocation at or after the authoritative cutoff. Receipt publication can happen later only for the exact transaction qualified below. The operator path, stores and authorized read/exports remain separate.

### Durability evidence and receipt publication

This clarification keeps the wire schema and approved window unchanged. It replaces any reading of the cutoff that requires a network response or the receipt-only transaction to complete by END. Until independently qualified, launch remains on HOLD.

1. **Data transaction.** Before END, validate enrollment, original, derived facts and capacity. Use one durable data transaction for the exact original, its accepted facts or quarantine disposition, and allocated archive sequence. A pre-COMMIT UTC reading is only an admission check, never the accepted-time witness. If validation or the pre-COMMIT cutoff gate fails, roll back. The successful transaction must actually finish inside the window.
2. **Witness.** Immediately after successful durable commit returns, take a trusted UTC sample in that uninterrupted writer invocation. Require `received_at <= witnessed_at < end` and a consistent clock/monotonic fence. The observation is a conservative upper bound on actual COMMIT completion, not a reconstructed timestamp. If it is exactly END, late, absent, regressed or uncertain, the operation has no qualifying acceptance. Preserve any already written bytes/facts as sealed incomplete evidence, withhold normal views and acknowledgement, and retain the failure record.
3. **Receipt-only finalization.** The original invocation may append a final immutable witness and the receipt atomically for that exact already-durable batch, including when this metadata COMMIT finishes after END. Bind enrollment/window, scoped batch, original digest/length, immutable fact or quarantine identity, original sequence and observed time. Recheck exact corresponding staged state and existing publication. The receipt's `committed_at` is the observed pre-END durability time and its `commit_sequence` is the original sequence. Record actual publication timing separately from the receipt when needed. This continuation writes no original, new fact, quarantine change or new sequence. Cutoff sealing blocks new ingress and does not block this narrowly scoped finalization. Never use later publication time as an earlier clock or run a new ingest to obtain a witness.
4. **Failure and recovery.** A crash or failed publication with no durable qualifying witness-and-receipt record leaves the transaction sealed. Presence of data rows alone does not prove an in-window COMMIT. No automatic orphan promotion, timestamp synthesis, retry-after-cutoff or later reprocessing into accepted pilot views. A durable completed witness/receipt can be verified and read after restart. Reopening must compare retained original, verified facts, sequence, enrollment and witness before treating the receipt as authoritative. Preserve both failed and successful evidence; keep sealed rows out of ordinary normalized views, exports and dependent acceptance. Historical “visible at” claims require actual publication evidence separately.
5. **After cutoff.** Device sends and retries stay off. The request may lose its response or remain unacknowledged; that does not prove a server rejection. The phone retains pending bytes under the existing rules. A scoped operator may later read the exact verified receipt for an in-window accepted commit. The finalization allowance does not reopen phone grants, sender retries or ingestion. Verify no post-END data commit qualified and no new sequence or facts were written after the cutoff; receipt-only metadata is a separate audited action.

Required synthetic race checks: (a) data commit observed before END, receipt metadata finishes after END, one unchanged accepted sequence; (b) data COMMIT starts before END and returns at or after END, sealed without normalized receipt/view; (c) crash after data COMMIT but before a durable publication witness, sealed through reopen; (d) crash after complete witness/receipt, exact authoritative readback after reopen; (e) cutoff marker lands between qualifying witness and receipt-only finalization, no new ingress, exact already-accepted receipt allowed; (f) clock regression or missing witness, fail closed. Check new PUT refusal and unchanged normalized state for incomplete cases. Use controlled barriers/fault injection rather than scheduling guesses.

Retain exact accepted originals, source/processing records, receipts, tombstones and revision lineage after cutoff without automatic age purge. Device deletion affects current view only and cannot erase an already accepted archival copy. Explicit archive erasure is separate. A finite ingestion window and storage quota do not establish an age-based retention limit. Protect originals and restricted keys/custody. No backup/restore acceptance follows from retention.

### Boundary vectors to implement before live activation

At exact synthetic start, accept an eligible point only when server and collector are in-window. Reject a point one microsecond before start or at cutoff. Accept a wholly contained sleep-stage or workout interval when completed in-window; exclude intervals crossing either boundary without partial rows. Test late but still in-window visibility, a future sample, unknown availability, a legacy unknown-UUID delete, an eligible prior-key and same-batch add/delete, mismatch window, and record receipt at cutoff. Test the durability and publication races above and a transport response lost before cutoff. Confirm no new data acceptance occurs after cutoff and no unverified outbox item is discarded. Reopen the unchanged authorized pre-cutoff state without resending. Confirm operator reads and original retention persist after ingestion stops.
