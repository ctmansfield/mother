# MSE synthetic privacy boundary contract

Provisional for local prototype under [MSE integration r8 / database privacy r2](https://github.com/ctmansfield/mother/pull/23#issuecomment-7045857604). The accepted custody and replay baseline is [#35](https://github.com/ctmansfield/mother/commit/b7aae4f2216d27f0544eab9fe9698286fe49d716). Evidence 0.2, original captures, receipt identities and reference bytes retain their authority. This prototype supplies no live privacy or deployment qualification. [Privacy assessment field inventory](../integration/PRIVACY_FIELD_INVENTORY.csv)

## Role, purpose and data class

Authorize each operation against a trusted grant binding authenticated identity, role, subject/source scope, purpose, active policy and generation. Roles below describe distinct capabilities. Keep protected namespaces and storage roots separate, and default deny. Request-supplied role, scope and cursor are inputs to validate, never authority.

| Role | Authorized purpose | Data class and permitted action |
| --- | --- | --- |
| Custody writer | evidence_ingest | Protected originals, capture metadata, acceptance journal and archive. Admit and verify source evidence. No analytics read token or vault lookup. |
| Exact MSE worker | exact_mse | Use an eligible receipt-backed 0.2 snapshot in a restricted execution boundary. Preserve exact clocks, eligibility, tombstones, channel/unit and derived lineage. No external read, raw artifact or identity-vault access through this role. |
| Projection worker | analytical_project | Read only the exact snapshot allowed by the active analytical policy. Produce the allowlisted analytical result. Ask the scoped registry to allocate opaque handles; no free-form linkage lookup or raw source path. |
| Analytical reader | aggregate_hr_sdnn | Read only an authorized projection, with its opaque handle and current authorization. No source snapshot, vault, original, exact MSE input, internal manifest or raw archive access. |
| Linkage/lineage resolver | lineage_audit | Resolve allowed opaque handles under independent authorization. Protect underlying IDs, digests and purpose bindings. No default export or archive-write capability. |
| Retention/recovery custodian | retention_recovery | Use task-specific access to the named backup or revocation store and role-separated restore. Restored data cannot bypass current generation or role checks. No automatic grant of normal read access. |

Use explicit permissions for allocate, project, read, resolve, revoke and restore. A service may implement multiple capabilities locally only if the entry points enforce role separation with genuinely separate test identities and no privileged fallback. These checks describe a local prototype. They do not resist a process with the same filesystem identity, host/root control or plaintext key access by themselves. Direct lower-layer exact, evidence and vault reads must be denied through the advertised analytical interface.

## Protected inputs and authorization

A protected view request binds authenticated principal, role, expected archive and source/subject scope, purpose, policy and projection versions, requested interval, verified receipt-backed input snapshot digest, and active grant generation. Bound input size, row count and time span before projection. Verify exact custody via the current trusted ledger. A status-only refusal uses a small allowlisted reason and an opaque operation reference if needed. Never echo user-provided identifiers, source strings, paths, clocks, backend exceptions or source facts to an analytical reader.

The exact MSE path consumes unchanged 0.2 within the designated boundary. It does not accept a reduced analytical view as a 0.2 input. The analytical worker may transform only an independently verified snapshot allowed for projection. It never edits authoritative time, facts, receipts or source state. Record precise transformation, scope, cutoff, loss counts and input/output linkage in a protected manifest.

## External analytical view 0.1

[Strict output schema](contracts/analytical-view-0.1.schema.json) · [Synthetic examples](contracts/analytical-view-examples.json). The initial policy is aggregate-only. No per-subject row token is needed. Allocate a random 128-bit-or-stronger `view_id` using standard system randomness. Bind the handle and internal artifact reference to purpose, subject scope, recipient, authorized operation, policy version, expiry and generation in restricted storage. The handle is opaque, not a credential. Never derive it from evidence or reuse it across purposes. Subject tokens, if a later policy needs them, require independent random purpose-scoped allocation and a separate reviewed schema.

For initial synthetic compatibility use policy `synthetic-aggregate-hr-sdnn/0.1` and projection `relative-hour-mean/0.1`. Their thresholds are prototype defaults, not accepted disclosure thresholds:

1. Bound the request to at most 24 hours. Bucket valid selected observation event starts by elapsed 60-minute intervals from the authorized interval start, without serializing that origin. Require the underlying interval to be complete in the requested window. A cross-bucket interval is assigned by its start and explicitly reported as a loss. Do not interpolate or infer absence from a suppressed or missing bucket.
2. Keep HR bpm and SDNN ms separate. Include only eligible positive, finite values with supported measurement class. Unknown HR derivation and nonpositive source-only facts remain protected and excluded. Do not reinterpret SDNN as RMSSD or raw RR. Respect tombstones and exact cutoff before projecting. Use the source-bound canonical decimal values. Arithmetic mean uses equal weight per eligible record, no intermediate rounding, and final rounding to one decimal, ties to even. Emit a fixed one-decimal string for an eligible positive mean. Suppress any rounded nonpositive result and disclose coarse loss.
3. Require three eligible contributions per bucket per channel for this synthetic policy. A suppressed bucket emits no row, count or marker for its position. Output rows are unique and sorted by (bucket_index, channel). Keep precision at one decimal. Do not expose exact counts, timestamps, absolute origin, date/time zone, native/subject/source IDs, raw values, device/source/bundle, path, locators or stable artifact/revision hashes. Do not publish the internal manifest as an analytical output.
4. Output coarse loss codes with no counts, per-record pointers or exact times. Show `relative_time_binning` and `value_aggregation_and_rounding` for any populated view. Use allowed codes for interval assignment, exclusion or suppressed/empty coverage where applicable. Sort and deduplicate. The private manifest may carry reasons, counts, precise affected references, scope and time policy. An empty result leaves coverage unknown.
5. Relative buckets can still correlate routines or rare events. Restrict release audience and overlapping query budgets. Calendar phase, exact durations and cross-source alignment cannot be recovered from this output. Exact-time work stays inside the authorized MSE boundary. Do not claim anonymity, clinical utility, or that a minimum of three readings means three subjects.

## Lifecycle and checks

The internal manifest stores the authorized purpose/role/recipient, current generation, expiry, exact immutable input reference, projection and policy versions, chronology/precision transformation, deterministic losses, and output digest under restricted access. Store analytical bytes separately. For identical pinned inputs and policy, result rows and loss codes are deterministic. Persist a random handle within its own authorized scope if a workflow needs stable readback. Do not use byte equality across independently allocated handles as a determinism test.

Check live authorization on every projection, read and resolution. For corrections, deletions, grant change or expiry, invalidate affected current projections, lineage resolution and downstream serving using generation/revocation state. A stale restore cannot reactivate revoked mappings. Keep authoritative revocation/generation state outside the restorable projection and linkage copies, and require fresh generation verification before serving restored data. Use role-separated backup and restore roots. An analytical restore cannot restore or mount the vault or raw evidence. A missing current registry/vault/generation denies access. Keep authoritative tombstones and historical receipts. Actual owner erasure needs a separate governed procedure covering originals, projections, logs, derived results, mapping and backups. Do not promise deletion of all historical copies through source-deletion semantics.

Proof for local prototype: cross-role/purpose/scope denials; expired and stale restored handle denial; no fallback on missing mapping; secrets/identifiers absent from output and error surfaces; unchanged source/reference digests; correct independent HR/SDNN unit, class, cutoff, interval and missingness cases; exact private lineage and bounded resolution. Validate strict schema plus semantic rules including order, unit pairing, no duplicate bucket/channel, and protected manifest agreement. Encryption, key custody, production retention, default disclosure controls and actual host compromise protection remain open.
